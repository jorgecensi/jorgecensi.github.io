# AGENTS.md

## Cursor Cloud specific instructions

This is a **Jekyll static site** (personal portfolio/blog) served on **port 4000**.

### Running the dev server

```
bundle exec jekyll serve --host 0.0.0.0 --port 4000 --livereload
```

### Key caveats

- **Bundle path**: Gems must be installed outside the workspace (e.g. `~/.bundle`) to avoid Jekyll scanning the `vendor/` directory and failing on invalid date frontmatter in bundled gem templates. The global Bundler config at `~/.bundle/config` sets `path: "/home/ubuntu/.bundle"` for this purpose.
- **No linter; tests only for Personal Trainer**: This project has no configured linter (ESLint, Rubocop, etc.). Site-wide validation is `jekyll build` (should exit 0) — but see the binstub caveat below before trusting a `bundle exec` failure. The Personal Trainer app additionally has a Playwright regression suite under `tools/personal-trainer-e2e/`; no other app has automated tests.
- **Fresh container: `bundle exec jekyll` may not resolve**: after a *successful* `bundle install`, `bundle exec jekyll build` can still fail with `bundler: command not found: jekyll` even though `bundle list` shows `jekyll (3.10.0)` installed. The binstub just isn't on PATH. Call the binary directly instead — `/opt/rbenv/versions/3.3.6/bin/jekyll build` (re-derive the path from `gem environment` → `EXECUTABLE DIRECTORY` if the Ruby version changes). Don't conclude the build is broken from the `bundle exec` failure alone.
- **Playwright must be pinned to match the pre-installed Chromium**: browsers live at `/opt/pw-browsers` and must never be re-downloaded. A bare `npm install playwright` pulls a newer version whose expected build directory doesn't exist, and launch dies with `Executable doesn't exist at .../chromium_headless_shell-<N>`. Pin it: `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install playwright@1.56.0` (matches build 1194 / Chromium 141). To re-derive the pin after an image update, read the build number from `ls /opt/pw-browsers` and match it against `node_modules/playwright-core/browsers.json`.
- **CodeQL is disabled — PRs receive no checks at all**: the `CodeQL` workflow has been `disabled_manually` since 2026-06-21, and no other workflow triggers on `pull_request` (the cache bump is push-to-master only). A PR reporting `state: pending` with `total_count: 0` is therefore the *terminal* state, not CI still spinning up — nothing will ever report. Don't wait on it or treat it as a stall; local `jekyll build` plus the e2e specs are the only verification available.
- **Stacked PRs are not auto-retargeted**: if you open PR B on top of PR A's branch and A then merges *without its branch being deleted*, GitHub silently leaves B based on that now-stale branch. Merging B lands the change on the stale branch instead of `master`, so it never reaches the site — and the PR still shows as merged, which makes it easy to miss. Always confirm a stacked PR's base is `master` before merging. (This is what happened to #293; #294 was the re-land.)
- **Build warning**: `Layout 'feed' requested in blog/atom.xml does not exist` is a known benign warning; it does not affect site functionality.
- **PWAs**: nearly all of the standalone apps under `README.md`'s app index (CrossFit Timer, Personal Trainer, Flappy Bird, Auto Runner, Elasto Mania, F1 Championship, World Cup 2026, Curator, Drum Machine, Synth, Tuner, Music Theory, Binary, Tennis Planner, Squeak the Geek) are fully client-side PWAs requiring no additional services.
- **Restarting `jekyll serve`**: `jekyll serve` (without `--watch`) reads files fresh from `_site/` on every request, so after editing a file just re-run `bundle exec jekyll build` — no server restart needed. If you do `pkill -f "jekyll serve"` to stop a `run_in_background` server, the harness reports that background task as "failed" (exit 144, i.e. SIGTERM) even though the kill succeeded; this is expected, not a real error — verify by curling the port or just start a new background server instead of killing the old one.
- **Save reusable tooling instead of rebuilding it each time**: when a task requires developing a non-trivial script, technique, or multi-step process (image processing, data transformation, a debugging workflow, etc.) that's likely to come up again, save the finished version under `tools/<topic>/` with a short README (and a GOTCHAS.md if you hit real failure modes worth remembering) instead of leaving it in an ephemeral scratchpad. Add a pointer to it from the relevant section of this file so it's rediscovered automatically next time — that saves re-deriving the same approach (and burning the tokens that took) from scratch. See `tools/character-sheet-extraction/` for an example.

### Personal Trainer app (`/personal-trainer`)

- **Keep the "How it Works" page in sync**: the `#info` screen in `personal-trainer/index.html` documents the progression mechanics in user-facing terms. Whenever those mechanics change — tier math (`SCORE_PER_TIER`, `MAX_SCORE`, `TIER_LABELS`, `tierCap`), feedback deltas (`FEEDBACK_DELTA`), dose growth (`doseFor`), exercise-pool selection (`pickPool`), rest durations (`restSecs` in `generateWorkout`), the streak window, or starting scores (`LEVEL_START`) — update the `#info` page copy in the same change so it never drifts from the code.
- **Bump the SW cache version on any PWA change**: when editing `personal-trainer/index.html`, `sw.js`, or `manifest.json` on a working branch, bump `CACHE_VERSION` (sw.js) and `SW_VERSION` (index.html) together so installed apps pick the change up. (A GitHub workflow also auto-bumps on merge to master, so an explicit bump is belt-and-braces, but new precached assets must be added to `PRECACHE_URLS` manually.)
- **Preferred video source for `PRESET_LINKS`**: the owner prefers the DAREBEE Exercise Library (YouTube playlist `PLQSMS0J6JbrKdSOSbyJXaQ_zN_HSSp7zZ`, videos titled "Exercise Library: <Name>") for exercise form-guide presets. When adding or updating presets, use the Darebee video if one exists for the movement; fall back to another clean landscape (non-Shorts) demo otherwise. Note: this environment's network policy blocks youtube.com/darebee.com, so discover Darebee video IDs via web search with exact-title queries like `youtube "Exercise Library: Side Planks"`.
- **E2E specs live in `tools/personal-trainer-e2e/`**: run them with `./tools/personal-trainer-e2e/run.sh` (all specs) or `./run.sh e2e.js` (named ones); it builds, serves, and reports pass/fail per spec. The suite is **fully green on `master`** — treat any failure as caused by your change, not as a known-red baseline. Read that directory's `README.md` first: it documents the pinned Playwright version (must match the pre-installed Chromium), and two navigation traps that bite new specs — the exercise library is reachable only via `#nav-settings`, and `[data-back]` buttons pop browser history rather than honouring their own `data-back="home"` value.
- **Mascot character sheets**: the owner has been supplying hand-picked mascot character sheets (multiple poses of one character per image, e.g. Barnaby the capybara) to give the app personality — see `img/pt/barnaby-*.png` for examples already integrated (feedback buttons, achievement-unlock toast). These sheets typically arrive with a *fake* transparent background (a checkerboard or solid color flattened into real RGB pixels, not an actual alpha channel). Use `tools/character-sheet-extraction/` to reconstruct real transparency and crop individual poses — read that directory's `README.md` first, and `GOTCHAS.md` before troubleshooting a pose that's missing detail (teeth, light-colored clothing, etc.) after extraction.
