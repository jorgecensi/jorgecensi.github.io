# AGENTS.md

## Cursor Cloud specific instructions

This is a **Jekyll static site** (personal portfolio/blog) served on **port 4000**.

### Running the dev server

```
bundle exec jekyll serve --host 0.0.0.0 --port 4000 --livereload
```

### Key caveats

- **Bundle path**: Gems must be installed outside the workspace (e.g. `~/.bundle`) to avoid Jekyll scanning the `vendor/` directory and failing on invalid date frontmatter in bundled gem templates. The global Bundler config at `~/.bundle/config` sets `path: "/home/ubuntu/.bundle"` for this purpose.
- **No linter; tests only for a few apps**: This project has no configured linter (ESLint, Rubocop, etc.). Site-wide validation is `jekyll build` (should exit 0) — but see the binstub caveat below before trusting a `bundle exec` failure. The Personal Trainer, Auto Runner, Elasto Mania, Music Theory and Chroma apps have Playwright suites under `tools/personal-trainer-e2e/`, `tools/auto-runner-e2e/`, `tools/elastomania-e2e/`, `tools/music-theory-e2e/` and `tools/chroma-e2e/`; no other app has automated tests.
- **Fresh container: `bundle exec jekyll` may not resolve**: after a *successful* `bundle install`, `bundle exec jekyll build` can still fail with `bundler: command not found: jekyll` even though `bundle list` shows `jekyll (3.10.0)` installed. The binstub just isn't on PATH. Call the binary directly instead — `/opt/rbenv/versions/3.3.6/bin/jekyll build` (re-derive the path from `gem environment` → `EXECUTABLE DIRECTORY` if the Ruby version changes). Don't conclude the build is broken from the `bundle exec` failure alone.
- **Playwright must be pinned to match the pre-installed Chromium**: browsers live at `/opt/pw-browsers` and must never be re-downloaded. A bare `npm install playwright` pulls a newer version whose expected build directory doesn't exist, and launch dies with `Executable doesn't exist at .../chromium_headless_shell-<N>`. Pin it: `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install playwright@1.56.0` (matches build 1194 / Chromium 141). To re-derive the pin after an image update, read the build number from `ls /opt/pw-browsers` and match it against `node_modules/playwright-core/browsers.json`.
- **CodeQL is disabled — PRs receive no checks at all**: the `CodeQL` workflow has been `disabled_manually` since 2026-06-21, and no other workflow triggers on `pull_request` (the cache bump is push-to-master only). A PR reporting `state: pending` with `total_count: 0` is therefore the *terminal* state, not CI still spinning up — nothing will ever report. Don't wait on it or treat it as a stall; local `jekyll build` plus the e2e specs are the only verification available.
- **Stacked PRs are not auto-retargeted**: if you open PR B on top of PR A's branch and A then merges *without its branch being deleted*, GitHub silently leaves B based on that now-stale branch. Merging B lands the change on the stale branch instead of `master`, so it never reaches the site — and the PR still shows as merged, which makes it easy to miss. Always confirm a stacked PR's base is `master` before merging. (This is what happened to #293; #294 was the re-land.)
- **Build warning**: `Layout 'feed' requested in blog/atom.xml does not exist` is a known benign warning; it does not affect site functionality.
- **PWAs**: nearly all of the standalone apps under `README.md`'s app index (CrossFit Timer, Personal Trainer, Flappy Bird, Auto Runner, Elasto Mania, F1 Championship, World Cup 2026, Curator, Drum Machine, Synth, Tuner, Music Theory, Binary, Tennis Planner, Squeak the Geek, Ding, Chroma, Cyber Quest) are fully client-side PWAs requiring no additional services.
- **Restarting `jekyll serve`**: `jekyll serve` (without `--watch`) reads files fresh from `_site/` on every request, so after editing a file just re-run `bundle exec jekyll build` — no server restart needed. If you do `pkill -f "jekyll serve"` to stop a `run_in_background` server, the harness reports that background task as "failed" (exit 144, i.e. SIGTERM) even though the kill succeeded; this is expected, not a real error — verify by curling the port or just start a new background server instead of killing the old one.
- **Save reusable tooling instead of rebuilding it each time**: when a task requires developing a non-trivial script, technique, or multi-step process (image processing, data transformation, a debugging workflow, etc.) that's likely to come up again, save the finished version under `tools/<topic>/` with a short README (and a GOTCHAS.md if you hit real failure modes worth remembering) instead of leaving it in an ephemeral scratchpad. Add a pointer to it from the relevant section of this file so it's rediscovered automatically next time — that saves re-deriving the same approach (and burning the tokens that took) from scratch. See `tools/character-sheet-extraction/` for an example.

### Auto Runner app (`/auto-runner`)

- **Everything lives in one file**: `auto-runner/index.html` is a single-file vanilla JS/canvas game (~1900 lines) in one IIFE — no build step, no dependencies. `STAGES` (difficulty/palette per 500m), `GROUND_POOL`/`CHUNKS` (obstacle spawning, validated by `validateChunk()` against the game's actual jump physics), and `ACHIEVEMENTS` (unlockable robot color pairs) are the main data tables to edit for balance changes.
- **Simulation is a fixed 60Hz step**, decoupled from `requestAnimationFrame` via an accumulator (see `loop()`) — never reintroduce per-rAF-callback physics constants, or the game will run at display refresh rate again (2x speed on 120Hz phones).
- **`?debug=1` exposes `window.__autoRunner`** (state/distance/stage/speed/mode/players/obstacles getters, `stepOnce()`, `setInput(idx, down)`) for automated testing, and logs chunk-validation results on load. Calling `stepOnce()`/`setInput()` even once disables the real rAF-driven loop for the rest of that page load — see `tools/auto-runner-e2e/README.md` before writing a spec that needs the *real* timing path instead.
- **E2E specs live in `tools/auto-runner-e2e/`**: run with `./run.sh` (all specs) or `./run.sh smoke.spec.js` (named ones). First run in a fresh container needs `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install` in that directory. Read that directory's README first — it documents the pinned Playwright version and the debug API.
- **The SW self-reload gotcha applies here too** (see the Personal Trainer note below on `clients.claim()`): a spec that waits or polls for more than a second or so after the first load should track `framenavigated` and settle before timing anything, or the SW-triggered reload can land mid-poll and destroy the execution context.
- **Bump `SW_VERSION`/`CACHE_VERSION` together** on any change to `auto-runner/{index.html,sw.js,manifest.json}`, same as the Personal Trainer convention below.

### Chroma app (`/chroma`)

- **Single file**: `chroma/index.html` listens to the mic and turns music into colour for deaf and hard-of-hearing users. It has no dependencies. The analysis (`analyse()`) reads two AnalyserNodes on one input bus: a 16384-point FFT for pitch (chroma, chord, key, melody, bass) and a 2048-point FFT for loudness, bands and onsets. The mic, the demo song and test tones all feed that same bus.
- **Drums are kept apart from notes**: `separate()` splits the 2048-point FFT into harmonic and percussive parts by median filtering (HPSS). Drum hits (kick, snare, hat) come only from the percussive part and are drawn in neutral white, never in a note colour. While a hit lands, the note colours hold still. `trackNotes()` finds notes with octaves, gives each a hand (`'L'`/`'R'`) from the moving `M.split`, and feeds the **Hands** view. The thresholds are tuned against the demo; see the tuning notes in `tools/chroma-e2e/README.md` before changing them.
- **Timbre and song shape**:
  - `sampleTimbre()`/`judgeTimbre()` give each note `env` (fade/hold), `move` (vibrato or wobble) and `bright`, read from a third analyser of about 85 ms (`A.mid`).
  - `structure()` sets `M.section` (build/drop/break) from 10 Hz history, and `M.pump` measures sidechain pumping.
  - Visuals map these to shape and texture, never to colour. Colour stays reserved for pitch.
  - Both demos (`startDemo({ song: 'band' | 'edm' })`) exist to exercise these.
  - Read the timbre tuning notes in `tools/chroma-e2e/README.md` before changing any threshold. Most of them came from a real failure, such as a vibrato partial leaking into a neighbour or octave doubling.
- **The mapping is the product, so keep it principled**:
  - Pitch class → OKLCH hue around the circle of fifths: `pcHue`, with C as red.
  - Chord quality → lightness and chroma: the `L`/`C` values in `QUALITIES`.
  - Key → background colour.
  - Loudness → brightness.
  - Tension (interval roughness plus chord type) → complementary halo and shake.
  - Pitch height → vertical position and lightness.

  The About overlay explains all of this in user-facing words. Update it in the same change if you change the mapping.
- **Photosensitivity**: full-screen pulses are capped at 3 per second (`V.lastFlash`, WCAG 2.3.1), and Calm mode softens them further. Don't add flashing that skips this cap.
- **E2E specs live in `tools/chroma-e2e/`**: run `./run.sh`. `demo-accuracy.spec.js` is the regression guard for chord detection, so run it after any change to the analysis. Read that directory's README for the `?debug=1` API.
- **Bump `SW_VERSION`/`CACHE_VERSION` together** on any change to `chroma/{index.html,sw.js,manifest.json}`.

### Cyber Quest app (`/cyber-quest`)

- **Single file, data-driven**: `cyber-quest/index.html` is a cybersecurity game in three tiers (`TIERS`: beginner, intermediate, advanced). All content lives in `MISSIONS` near the top of the script, in play order; each mission has a `tier`, and each question has a `kind` (`email`, `url`, `chat`, `choice` with optional `code` snippet, `lines` = tap the bad line, `order` = tap `items` in their correct order, `forge`), an `answer` (not for `order`) and an `explain` (raw HTML, so write `&lt;` for literal tags). Email red flags are `<mark class="flag" data-n="N">` spans in the email HTML, numbered to match the `flags` array; they stay unstyled until the answer is revealed. For `url` questions, `domain` must be the registered domain (it's highlighted after answering and must appear at the end of the host).
- **Keep the teaching accurate**: every answer shows its `explain` text, and clearing a mission adds its `tips` to the Field Guide. When you add or edit a question, make sure the explanation says *why*, not just what.
- **Progression**: missions unlock in `MISSIONS` order, and each tier's last mission is its boss (`boss: true`), so beating a boss unlocks the next tier's first mission. A boss unlocks once every mission in its tier is cleared, and it draws `count` random non-forge questions from its own tier, with a `time`-second timer each. XP per correct answer is the tier's `xp` (+5 for bosses); keep `RANKS` reachable if you add missions. Mission ids are progress keys, so never rename one (the beginner boss is still `boss`).
- **Progress** is in `localStorage` under `cyber-quest-progress-v1` (`{ v: 1, missions: { <id>: { stars, xp } } }`); XP is the sum of each mission's best run, so replays can't farm it.
- **Terminal Ops** (`LABS`, the `Ops` object): a simulated Linux shell on an in-memory filesystem where the player defends a fictional server with real commands (`ls`/`cat`/`grep`/`ps`/`kill`/`chmod`/`find`/`ss`/`ufw`/`systemctl`, plus a single pipe into `grep`/`head`/`tail`/`wc`). Each lab has a `build()` returning a fresh `{ fs, procs, net, services }` (so replays reset), and `tasks` with a `check(T)` run against live shell state (`T.read`, `T.killedCmds`, `T.ufw`, `T.stoppedSvc`, node `mode` strings, `T.ran(regex)` over history). Commands are deliberately forgiving; keep them so, and keep every scenario safe/fictional (RFC 5737 IPs, fake creds). Lab ids are progress keys under `progress.labs` — never rename one. Labs unlock in array order (a cleared lab never re-locks), grouped by `stage` (`LAB_STAGES`: `basics` teaches from zero, `ops` are the incident labs). Every task has a `lesson` (authored HTML shown in the 📖 panel above the terminal for the first unfinished step): explain the concept, then the command. Incident lessons should point back to the Basics lab that taught the skill, and an incident lab must only need skills a Basics lab teaches. A task with `answer` is completed with the `answer <text>` command (its `wrong` text is the retry nudge).
- **`?debug=1` exposes `window.__cyberQuest`** (`state`, `progress`, `answerCorrect()`, `answerWrong()`, `next()`, `analysePassword()`, `labs`, and `ops` = `{ open(id), start(), run(cmd), done, tasks, out }` for driving the terminal). No e2e suite yet.
- **Bump `SW_VERSION`/`CACHE_VERSION` together** on any change to `cyber-quest/{index.html,sw.js,manifest.json}`.

### Music Theory app (`/music-theory`)

- **Single file**: `music-theory/index.html` holds the whole app (Tone.js sampler, keyboard, explore tabs, free-play Quiz, and the guided **Learn** path). Learn data (`LEARN_UNITS`, the "why" copy) sits in the data section near the top; the Learn engine is its own `// ── Learn ──` section. Learn reuses the quiz core (`beginRound()`, the pool-parameterised generators, `registerQuizKey`/`checkQuizAnswer`), so a change there affects both tabs — run the e2e suite after touching it.
- **Progress persists** in `localStorage` under `music-theory-progress-v1`; keep the shape documented in `tools/music-theory-e2e/README.md` in sync if you change it, and bump `v` on a breaking change.
- **Adding or reordering Learn units**: `learn.unitIdx` is a position in `LEARN_UNITS`, so inserting a unit shifts every later one. Bump `LEARN_LAYOUT`, keep the previous order as a `LEARN_LAYOUT_<n>` id list, and map old saves by id in `loadProgress()` (see the layout-1 migration). Each unit should only quiz intervals, chords or scales an earlier unit has introduced.
- **`?debug=1` exposes `window.__musicTheory`** (state, progress, units, `answerCorrect()`/`answerWrong()`/`gotIt()`, `switchMode()`, `resetProgress()`) for automated testing; answers register even when the piano samples never load, so specs don't need network access to tonejs.github.io.
- **Interval song references** live in `INTERVAL_REFS` (by direction and semitones). Each `tune` is a public-domain melody, or a short teaching `figure` where no well-known one exists, written as offsets from the interval's first note, so the Hint plays it on the question's own notes. Keep the interval as an adjacent `0 → ±n` step: `interval-hints.spec.js` enforces it. `pop` entries embed YouTube on demand via `youtube-nocookie.com`. This environment can't reach YouTube, so find video IDs with web search (`allowed_domains: youtube.com`), and only add a song when a source gives the notes and they check out by counting semitones, or a dedicated ear-training publisher (Musical U) names the exact lyric. One popular list claims A→G in "Take On Me" is a major 7th; it is a minor 7th. The owner prefers songs from 2000 on: keep an older recording only where no well-sourced modern one exists, and give every entry a `year`. Use `start` (seconds) when the interval isn't near the beginning.
- **Instruments**: piano is the Salamander sampler (remote), Electric piano a Tone.js synth, and the 19 others are recordings from tonejs-instruments, self-hosted in `music-theory/samples/` (about 11 MB; credits in `samples/CREDITS.md`) and listed with their sampled `notes` in `INSTRUMENTS` near the top. Rebuild or add samples with `tools/music-theory-samples/` (read its README: one source file is mislabeled, and `check_pitch.py` has expected false positives). All playback goes through `voice()` and `instrumentReady()`. `beginRound()` calls `chooseRoundInstrument()`: Learn picks a random *loaded* instrument whose range covers the question's notes when `progress.settings.learnMix` is on (the default), as does any round when the picker (`progress.settings.instrument`) is `'random'`. Explore tabs always use the picker's choice. The SW caches `/music-theory/samples/` in the persistent `mt-samples-v1` cache, so version bumps don't re-download them.
- **Hinted Learn rounds don't count** towards passing a step, and "Play the key first" (`progress.settings.keyContext`) prefixes interval prompts with I–IV–V–I in the lower note's key.
- **Learn game layer** (all in the `// ── Learn ──` section):
  - *Variants*: each hear/play round is picked by weight from `LEARN_VARIANTS` (standard, song, odd one out, wrong note, count the bars; blind, finish the phrase, complete the chord, missing note). `variantAvailable()` drops a variant a unit can't serve. Every variant draws only on what the unit already teaches and records into the same step stats. A variant that plays its own prompt sets `q.events` (`playQuestion()` plays those first) and lists every note it sounds in `midis`/`extraMidis`/`givenMidis`, so random instrument picks can reach them. Song variants reuse `INTERVAL_REFS` tunes and `SONGS`, so the sourcing rules above apply. The pulse unit's song rounds play `METER_SONGS` (public-domain tunes with their meter and pickup, no clicks); a duple tune accepts 2/4 or 4/4 through the question's `accept` list. Real recordings for that unit live in `METER_POP` (the `video` round, which embeds the song in `#learn-video` and is skipped offline and in boss/daily runs, and the after-answer card from `renderMeterRefs()`). Add a song there only when sheet music or Wikipedia states its meter: much pop that feels "in three" is printed in 6/8 or 12/8. The "Beyond 4/4" unit (`more-meters`, after Major & minor chords; layout 3) adds 2/2, 6/8, 12/8, 5/4 and 7/4. Meters that only differ on paper (`SAME_FEEL`: 2/4–2/2–4/4, 6/8–12/8) accept each other for tunes and recordings; click rounds only pair 2/2 with 2/4 (`SAME_CLICKS`), since clicks do show 4/4's beat-3 accent and 12/8's extra beats. The Measures quiz leaves 2/2 out.
  - *Facts*: one-liners in `UNIT_FACTS`, `INTERVAL_FACTS`, `CHORD_FACTS` and `SCALE_FACTS` show after each answer. They teach, so keep them accurate and one sentence long.
  - *Boss*: every unit's steps end in `boss` (`unitSteps()`), named in `UNIT_BOSSES`. `gotIt()` opens it; only a won boss run (`completeUnit()`) marks the unit done and moves the frontier. Runs (`startRun('boss'|'daily')`) are left (`abandonRun()`) on any navigation or tab switch.
  - *XP and combos*: `awardAnswer()` gives 10 XP times the combo multiplier (x2 from 5 in a row, up to x4). Hinted rounds earn nothing.
  - *Daily mix*: ten questions from every unit whose Hear step passed. The first one each local day grows `progress.daily.streak`; a missed day resets it.
  - *Singing*: with `progress.settings.sing`, interval play rounds become `sing` rounds judged by the mic (`detectPitch()` is the Tuner app's autocorrelation). Any octave counts. The keyboard still answers them. The mic is released when the page is hidden or Learn is left.
  - *Sound effects* use their own small synth (`sfxVoice()`), never the round's instrument, and stay silent until audio has been started by a tap.
  - *Layout*: a round shows one header line (unit button, XP and streak chips, settings), a segmented step bar, then the question as the hero (a big Play button, large answers) and, once answered, one result card with a full-width Next. Set-once options live in the settings sheet and the unit list plus the Daily mix in the path sheet (both `.sheet`, outside `#controls-panel`, which clips). Boss and daily runs use focus mode (`body.learn-focus`): the app header and tabs hide and `renderRunBar()` draws the run header, hearts and a segment per question, with the timer as a ring around Play. In portrait `#panel-learn` takes the height the piano leaves (`--learn-chrome`); landscape has its own compact rules, so check both orientations after a layout change.
- **E2E specs live in `tools/music-theory-e2e/`**: run `./run.sh` (all) or `./run.sh smoke.spec.js`. First run in a fresh container needs `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install` there. Read its README first. `learn-game.spec.js` launches a second browser with Chromium's fake-microphone flags to test singing end to end.
- **Bump `SW_VERSION`/`CACHE_VERSION` together** on any change to `music-theory/{index.html,sw.js,manifest.json}`.
